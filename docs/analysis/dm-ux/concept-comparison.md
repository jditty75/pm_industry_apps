# Concept comparison

Scores each concept against the eleven dimensions instruction 28 specifies. STRONG / MODERATE / WEAK plus rationale. Comparison is relative to the other two concepts and to today's DM, not to an abstract ideal.

| Dimension | Concept A — Evolve in place | Concept B — Deployment-centric | Concept C — Grouped navigation |
|---|---|---|---|
| Current-user familiarity | **STRONG** — tab order, labels (bar one rename), and all interaction patterns unchanged. Zero retraining. | **STRONG** — identical top-level nav to today; the drawer is additive and opt-in to notice. | **WEAK** — every existing tab moves one click deeper except each group's default child. Real retraining for every daily user. |
| Information density | **MODERATE** — unchanged page density, but token/contrast fixes slightly reduce the lowest-size text, a small density cost for a correctness gain. | **MODERATE** — same as A on existing pages; the drawer itself is narrower (~40% viewport) and needs its own compact layout, an added design burden, not a density loss on the main pages. | **WEAK-to-MODERATE** — two-level nav consumes vertical space (group row + sub-nav row) that today's single row doesn't, directly competing with the "information-dense first screen" goal. |
| Scalability (future features) | **WEAK** — a 6th or 7th top-level tab still just adds to one flat row; no structural headroom beyond what exists today. | **MODERATE** — top-level scalability is unchanged from A (same weakness), but the drawer absorbs growth in *deployment-related* detail without ever needing a new top-level tab — half the scalability problem, solved. | **STRONG** — explicitly designed with headroom; a 5th, 6th, 7th feature joins an existing group's second level without growing the first level at all. |
| CSAT fit | **STRONG** — CSAT gets a complete, well-structured home as one tab with 5 sections; fully meets instruction 6 ("CSAT remains one top-level feature with internal navigation"). | **STRONG** — same CSAT tab as A, plus the response-timeline/CSAT-in-drawer view gives CSAT a second, complementary entry point (via any deployment) without duplicating navigation. | **MODERATE** — CSAT content is identical to A/B, but it now sits one click behind "Customer Experience," which groups it sensibly with Notable but makes it less immediately scannable in the primary bar than today. |
| Deployment context (4–7-areas problem) | **WEAK** — not solved; this is the gap the discovery flagged most clearly, and Concept A leaves it in place. | **STRONG** — this is the concept built specifically to solve it; one surface, reachable from everywhere a deployment is referenced, with deep links. | **STRONG if paired with B's drawer** (as this document assumes in `concept-c-grouped-navigation.md` §4); **WEAK on its own** — grouping tabs doesn't by itself reduce the number of places a deployment's information lives. |
| Family-wide consistency | **STRONG** — same mechanism as today (config-driven flat tab list), no new divergence introduced. | **STRONG** — adds one new surface, but its presence/section-list is config-driven exactly like today's tabs; no new kind of per-app divergence. | **MODERATE** — apps now differ in *how many top-level groups render* (2 for HS, 3 for SLG/HC/HENP, different-3 for PDX), a more visible structural difference between apps than today's same-shape-different-length single row. |
| Accessibility | **STRONG** — same fix set as every concept shares (tab/dialog semantics, contrast, forms, tables, motion); no concept-specific new surface to audit. | **MODERATE** — inherits A's fixes, plus one genuinely new interactive surface (the drawer) needing its own dialog/focus-trap/non-modal decision — more to get right, not harder in kind. | **MODERATE** — inherits the same baseline, plus a new first-level control needing its own keyboard model (tablist vs. disclosure pattern) — comparable new-surface cost to B's, different surface. |
| Implementation complexity | **STRONG (lowest)** — token cleanup, one sub-nav component, one modal shell, CSAT tab content. No new top-level mechanism. | **MODERATE** — all of A's work, plus a new drawer component, hash-based deep-link state, and relocating several modals' detail content without breaking their edit flows. | **WEAK (highest)** — all of A's work, a new group-level nav mechanism touching every `CoreConfig.js`/`CoreUI_Markup.js` tab-enablement check, empty-group suppression logic, and (if paired with B) the drawer too. |
| Migration risk | **STRONG (lowest)** — additive changes to one tab (CSAT) and shared-component cleanup elsewhere; very low chance of regressing an existing workflow. | **MODERATE** — new surface risk is contained (if the drawer has bugs, existing tabs are unaffected), but relocating modal content risks breaking a currently-working edit flow if not done carefully. | **WEAK** — changes the thing every user touches on every single visit (top-level navigation); any defect in group logic (e.g., an incorrectly-empty group, or lost group-membership state) is maximally visible. |
| Maintainability | **STRONG** — fewer CSS/component families (that's the point of the token/component consolidation), same navigation mechanism to reason about. | **MODERATE** — one more component family (drawer) to maintain, but it replaces rather than duplicates several existing modals' content, a net wash or small win. | **WEAK** — two navigation mechanisms to keep consistent (group-level + sub-nav level) instead of one, and the config schema for "which group am I in" is new surface area that has to stay correct as apps' feature flags change. |
| Future feature growth | **WEAK** — same ceiling as today; a 6th feature still competes for flat-bar space. | **MODERATE** — deployment-related growth (more things worth knowing about one deployment) is well-absorbed by the drawer; feature-level growth (a wholly new top-level capability) is not better-absorbed than today. | **STRONG** — explicitly the concept designed for this; the entire argument for Concept C is future headroom. |

## Reading the matrix

No concept sweeps the table, and none should — instruction 12 asked for genuinely different concepts, and the scores reflect genuinely different tradeoffs, not a hidden preference. Three patterns are worth naming explicitly:

1. **A and B are nearly identical except on the one dimension B exists to fix.** B inherits every one of A's STRONGs and only trades MODERATE-not-STRONG on three dimensions (density, accessibility, implementation complexity/migration risk) in exchange for turning the 4–7-areas problem from WEAK to STRONG. That is a narrow, legible trade.
2. **C is the only concept with a real STRONG on scalability and future growth**, but it is the only concept that is WEAK on current-user familiarity, and it carries the highest implementation/maintainability cost of the three. Its case rests entirely on whether DM's tab count is actually close to a breaking point — and per the discovery, today's realized counts (7 for EVI/HS up to 9 for SLG/HENP) are not yet there. C's strength is a bet on a future that hasn't arrived.
3. **The deployment-context problem (4–7 areas) is real today, evidenced directly in the discovery, and only B solves it without also paying C's familiarity and complexity cost.**

See `recommended-direction.md` for the recommendation this matrix supports.
